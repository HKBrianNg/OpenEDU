> 文档版本：v4.0  
> 最后更新：2026年7月

## 二、架构设计原则

| 原则 | 说明 |
|------|------|
| **前端不直连数据库** | 所有数据操作必须经过后端 API，前端仅通过 Axios 调用后端接口 |
| **后端持有数据库密钥** | 后端使用 Supabase Service Key 操作数据库，前端完全不感知数据库结构 |
| **权限在后端控制** | 用户身份验证、角色校验、操作授权全部在后端中间件中完成 |
| **API 统一入口** | 所有功能通过 RESTful API 暴露，便于版本管理和安全审计 |

## 三、数据流向
用户操作
↓
前端 (React 19) → Axios 请求 → /api/*
↓
后端 (Express 5) → 验证 JWT → 校验权限
↓
后端使用 Supabase Service Key 操作数据库
↓
返回结构化数据给前端

## 四、架构分层图
**前端完全不包含以下操作：**
- ❌ 直接调用 `supabase.from('articles').select()`
- ❌ 直接访问数据库表名或字段名
- ❌ 直接使用 Supabase Anon Key 进行数据库查询

## 八、用户注册完整流程
用户填写邮箱 + 密码 → 点击注册
↓
POST /api/auth/register
↓
后端验证邮箱是否已存在
↓
密码 bcrypt 哈希
↓
写入 users 表 (status = unverified, role = reader)
↓
生成6位数字验证码，存入 Redis 或内存缓存（有效期10分钟）
↓
通过 nodemailer 发送验证码到用户邮箱
↓
用户输入验证码 → POST /api/auth/verify-email
↓
后端验证验证码是否正确且在有效期内
↓
验证通过 → users.email_verified = true, users.status = pending
↓
用户状态变为 "pending"（等待管理员审核）
↓
管理员登录后台 → GET /api/admin/users/pending
↓
管理员审核 → PUT /api/admin/users/:id/review
↓

├── 审核通过 (approved: true)
│       → users.status = active
│       → 发送通知邮件 "您的账号已通过审核"
│       → 用户下次登录即可正常使用
│
└── 审核驳回 (approved: false, reason: "...")

→ users.status = rejected
→ users.rejected_reason = reason
→ 发送通知邮件 "您的注册申请未通过审核，原因：..."
→ 用户登录时会收到驳回提示

### 用户状态流转图

unverified (未验证邮箱)
↓ 验证邮箱
pending (待管理员审核)
↓
├── active (正常)    ← 管理员审核通过
└── rejected (驳回)  ← 管理员审核驳回
↓
disabled (禁用)      ← 管理员手动禁用（可从 active 或 rejected 状态进入）

## 九、内容状态流转

draft (草稿)
↓ 作者提交审核
pending_review (待审核)
↓
├── published (已发布)    ← 管理员审核通过
│    ↓
│   unpublished (下架)    ← 作者或管理员取消发布
│    ↓
│   draft (草稿)          ← 重新编辑后可再次提交
│
└── rejected (驳回)       ← 管理员审核驳回

↓
draft (草稿)           ← 作者修改后可再次提交

## 十、多语言支持方案

| 内容类型 | 实现方式 |
|---------|---------|
| 前端 UI 文案 | 前端 JSON 文件 (`src/locales/*.json`) |
| 后端错误消息 | 后端 JSON 文件 (`constants/messages.json`)，根据 `Accept-Language` 头部返回对应语言 |
| 邮件模板 | 后端 JSON 文件 (`templates/*.json`)，每种语言一套 |
| 用户语言偏好 | `user_preferences.language` 字段，前端 Axios 拦截器自动携带 |
| 文章标题/内容 | `articles` 表存储原文，多语言版本为后续扩展（暂不实现） |

支持三种语言：
- **简体中文 (zh-CN)**
- **繁體中文 (zh-TW)**
- **English (en)**

## 十一、日志体系

| 日志类型 | 存储位置 | 用途 | 访问权限 |
|---------|---------|------|---------|
| **操作日志** | `audit_logs` 数据库表 | 追溯用户操作、审计合规 | 仅管理员可查看 |
| **系统日志** | 服务器文件 (Winston) | 排查故障、监控运行状态 | 开发者/运维 |
| **访问日志** | Nginx 文件（如使用） | 流量分析、安全审计 | 运维 |

### 操作日志记录规范

所有涉及数据变更的操作都需要记录审计日志：

javascript

await auditLog(userId, 'article.create', 'articles', newArticleId, {

title: '文章标题',

ip: req.ip,

});

操作日志命名格式：`{实体}.{动作}`

article.create      创建文章
article.update      编辑文章
article.submit      提交审核
article.review      审核文章
article.unpublish   取消发布
user.register       注册
user.approve        审核通过用户
user.reject         审核驳回用户
user.disable        禁用用户
user.enable         启用用户
category.create     创建分类
category.update     编辑分类
category.delete     删除分类
comment.create      发表评论
comment.delete      删除评论

## 十四、关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| **数据库访问方式** | 后端独占，前端不直连 | 安全性、统一权限管控、隐藏数据结构 |
| **后端数据库凭证** | Supabase Service Key | 最高权限，绕过 RLS，由后端自行控制 |
| **认证方式** | 自定义 JWT，不依赖 Supabase Auth | 完全掌控认证逻辑和用户生命周期 |
| **权限控制** | 后端中间件 | 集中管理，清晰可审计 |
| **多语言翻译** | JSON 文件，不入数据库 | 轻量、易维护、无需额外查询 |
| **HTTP 客户端** | Axios | 拦截器统一处理 Token/错误/语言 |
| **日志** | 操作日志（表）+ 系统日志（文件）双轨 | 审计需求 vs 运维需求分离 |
| **邮箱验证** | 验证码机制，10分钟有效期 | 平衡安全与用户体验 |
| **用户审核** | 管理员人工审核，通过后邮件通知 | 控制平台用户质量 |
| **文件上传** | 后端代理上传到 Supabase Storage | 统一鉴权，避免前端直接暴露存储桶 |
